# 联系人与群聊

> 文档状态：Active<br>
> 面向读者：设计者、前端与 Core 开发者、维护者<br>
> 最后核验：2026-11-06<br>
> 事实源：本文是 0.3 的设计稿，实现后以 `packages/core/src/contacts/`、`packages/core/src/groups/`、`desktop/src/renderer/src/components/contacts/`、`desktop/src/renderer/src/components/groups/` 及其测试为准

联系人是长期存在的 agent：有名字、头像、一份岗位说明书、自己的模型、工具和记忆。群聊把几位联系人拉进同一个会话，谁对谁说了什么、为什么交给谁、交出了什么，都摆在一条时间线上，用户随时能插话、点名、停止。它们都在 [Group 模式](modes.md)里。

## 联系人

### 岗位说明书

每个联系人是一份七节的岗位说明书，编译成固定结构的系统提示词（同样的输入，输出逐字节相同）：

| 节           | 内容                                                                                          |
| ------------ | --------------------------------------------------------------------------------------------- |
| 1 身份       | 名字（1–24 字，不重名）、头像、一句话简介（≤ 60 字）、领域（最多 3 个）                       |
| 2 职责与交付 | 负责什么、交出什么、什么格式                                                                  |
| 3 工作方法   | 步骤与检查清单                                                                                |
| 4 知识       | 只读资料：文件、文件夹、网址、用户写的笔记；常驻资料合计 ≤ 8 KB，其余按需读取；回答时注明出处 |
| 5 边界       | 不做什么、什么时候交还、不确定时怎么标                                                        |
| 6 能力       | 选中的 Skill、MCP 服务与具体工具、模型、工具预设、权限（不能高于全局权限）                    |
| 7 群聊习惯   | 什么时候开口（只在被点名时 / 和职责相关时举手 / 总是发言）、篇幅（简明 / 详细）               |

- 每次保存生成一个版本，保留最近 20 个，可以对比和退回；群里永远用最新版。
- 资料和网页内容当数据，不当指令：工具权限只由岗位说明书决定。
- 记忆分两部分：用户的明确反馈（👍 / 👎 加一句话）和它自己从工作里整理出的经验；只对这个联系人生效，可以改、停用、删除、恢复。
- 联系人不用主记忆（`MEMORY.md` / `USER.md`），普通对话和 Build 照旧；联系人会话在升级时画一条上下文边界，边界前的历史只供查看，不再进入模型请求。
- 知识、能力、经验是 schema 3 的顶层字段（`knowledge` / `skills` / `mcp`）；旧联系人的 `role.knowledge` 在升级时迁入，Skill 引用变成 `skills`（来源标 `legacy`），迁移前备份 `contacts.schema2-<时间>.bak.json`。

### 专业化补丁（CP-01..06）

- 知识与能力分开：知识只放文件、文件夹、网址、笔记；Skill 和 MCP 进能力，由 Core 的统一解析器决定目录、加载、工具 schema 和实际执行，选中的 Skill 只有它自己能用，子代理继承同一选择，deny 优先。
- 经验自动积累：一项工作结束且宿主核对到工具结果、用户确认或用户纠正时，后台再调用一次小模型提炼（每次 ≤5 条、≤800 Token，费用计入「用量与费用」）；没有依据的只进待验证，不召回。召回按联系人与作用范围（contact/project/group/session）在 4 KB 内取最新的有效经验。
- 旧反馈没有稳定来源时不召回：原 Markdown 保留，进「历史反馈（待确认）」。
- 外部 Claude Code / Codex 仍不接宿主 Skill/MCP；选择器标「不支持」，不假装已生效。

### 四种建法

在 Group 模式侧栏点「+」（新建联系人），或在联系人页右上「新建联系人」，打开编辑器。四种建法都只填编辑器，点「保存联系人」才保存：

1. **从岗位模板**：18 个模板，按领域分组——软件工程（架构师、代码审稿人、测试工程师、安全审计、前端工程师、运维与发布）、设计（素材设计师、界面设计评审）、内容（研究员、写作者、编辑、译者、市场文案）、产品与决策（产品经理、用户研究员、数据分析师、反方（红队）、主持人）。模板要的权限高于新会话的权限时，从只读开始。
2. **说说你要什么人**：用户写几句描述，点「起草」后 Emperor 用默认模型做一次结构化输出：信息不够时最多追问 3 个问题，回答后直接起草。起草的节标「AI 起草」，用户改过就去掉；起草失败时描述留着，可以再试。起草和试用台都是真实的模型调用，只在用户点按钮时发生。
3. **导入**：Claude Code 的 `agents/*.md` 或现成的提示词文件，只读用户选的那一个文件，不超过 64 KB。`name` 成为名字，`description` 成为简介（截到 60 字），`model` 只作提示，正文进「工作方法」；工具按表转换（Read、Grep、Glob、Bash、Edit、Write、WebSearch、WebFetch），其余列为「没有导入」；frontmatter 坏了时整个文件进「工作方法」并提示。导入的文字是资料，工具只按表来。
4. **复制已有联系人**：用户自己建的联系人，名字加「副本」。

编辑器右边有完整度检查（交付、≥ 2 步方法、边界、工具与权限一致、跑过试用台；只提示，不阻止保存）、试用台和生成的系统提示词预览（和运行时编译的完全一样）。试用台用还没保存的设置在隐藏会话里跑一次样例任务，显示结果、用量和花费；需要批准的操作和提问都会被拒绝，关掉编辑器就停止，隐藏会话 24 小时后清理，不出现在任何列表和搜索里。内置联系人只能改头像和简介；外部联系人的模型和权限跟随「设置 › 子智能体」。

### 头像

- 头像库：135 个 Q 版头像，15 个主题（工程、设计、内容、产品、文臣、武将、宫廷、混搭、动物、机器人、人物、奇想）。
- 新建时**先推荐**：从模板新建时先用模板的默认头像，别人在用就从模板对应主题里随机挑一个，跳过别的联系人已在用的（空白、起草、导入的从人物、动物、机器人里挑）。旁边有「换一个」（同主题再随机，这次编辑里推荐过的都不再出现，全都用过时才允许重复）和「从头像库选…」（按主题分组、可搜索；别人在用的标「在用」，仍然可以选，选了会提示谁也在用）。头像的名字和主题跟编辑器一起加载（编辑器本身是单独的一块，不进入口包），所以推荐行一开始就写「推荐：安全审计」；读不到时写主题（「推荐：工程主题」）。之后在联系人档案里也能换（「换头像」打开头像库）。
- 内置联系人：Emperor 用吉祥物小单戴冠的头像；Claude Code、Codex 用厂商标志。子智能体仍用原来的毛绒动物头像，和联系人区分开。

### 档案与单聊

- 联系人页（`/contacts`，GRP-21）：主区域整页，像「能力」页一样（标题「联系人」、副标题、右上「新建联系人」，内容列 880 居中）。标题下是分类条（下划线页签，带数量），再往下是平铺的联系人卡片（头像、名字、两行简介、领域标签；外部写「外部 · 只读」）。分类按联系人的 `domains`：产品、工程、设计、内容、数据、安全、决策；Claude Code、Codex 只进「外部」；没有领域（或领域是 `other`）的进「其他」兜底；没有联系人的分类不显示。点一张卡片进入档案：分类条和卡片收起，左上「‹ 所有联系人」返回，原来的分类还在。侧栏保持群聊列表。点底栏的联系人图标打开它，再点图标或点侧栏里的群回到会话。
- 档案（`/contacts/:id`，GRP-05、GRP-21）：是联系人页的详情视图（分类和卡片收起，上面有「‹ 所有联系人」），也可以直接打开。头像（「换头像」）、名字、领域和简介；「发消息」「拉进群」（列出群，选一个就把它加进去并打开那个群，GRP-08）「编辑」；四个数字（Core `contacts.stats`）：参与的群（现在是成员的群）、发言次数（群里的发言，不含「没有补充」和系统消息，加上它单聊里的回答）、你的评分（个人记忆里还留着的 👍 占全部 👍 / 👎 的比例，「83%」「你的评分（12 次）」；还没有时写「—」）、岗位说明书版本。标签页：职责与方法、知识（文件/文件夹/网址/笔记，常驻或按需）、能力（Skill、MCP 工具与可用状态；外部智能体标明不支持绑定）、记忆（工作经验按有效/待验证/已停用/已删除筛选，可改、停用、删除、恢复；下方是用户反馈；开关；内置联系人的开关不能动）、版本。新建联系人保存后进它的档案。
- 版本标签页：当前版本在最上面，然后是旧版本，新的在前。下面对比两个版本（默认上一个版本对当前版本，两个下拉框可以选任意两个，旧版本行上的「和当前对比」直接选它），逐项列出不同的地方（名字、简介、领域、职责、交付、工作方法、知识、工作技能、外部连接、边界、模型、工具、权限、群聊里发言、发言篇幅、个人记忆）。「退回到 vN」先确认，退回产生一个新版本，历史不变。
- 「发消息」打开和这个联系人最近的单聊，没有就新建（Core `contacts.openChat`：只看 `surface: 'contact'` 的会话，试用台、群成员会话不算，`/clear` 换掉的旧会话也不算）。单聊就是普通会话，日志、压缩、计划模式、目标、工作台都照常；`/clear` 之后新会话仍是这个联系人的单聊。它属于 Group 模式；从档案回联系人页就能看到它所在的分类和卡片。
- 单聊里每段回答上方是联系人的头像和名字；空的单聊首页写联系人的名字和简介，输入框提示「给「审稿人」发消息」。回答的底栏（指针移上去时出现）有 👍「有帮助」/ 👎「没帮助」，点了写一句为什么（可以不写），「记下」写进它的个人记忆（`contacts.feedback`，带上这段回答的消息 id）；个人记忆关着时没有这两个按钮。联系人被删除后单聊只读，输入框写「这个联系人已删除，这个会话只能查看」。
- Claude Code、Codex 的单聊（GRP-11）不跑本地回合：单聊里的消息交给它们自己，是一个以单聊会话为根、由用户开的委派（`owner.source: 'contact'`）。第一条消息开委派（`contacts.chatSend`），只读（`shared-readonly`，没有项目时在单聊自己的工作目录里），之后的消息续这个委派，每条消息各算一个任务：发出时开始一个新任务，花费从零算起（GRP-19），所以聊得再长也不会碰到「每个任务最多外部运行」，「设置 › 用量与费用」的费用上限也只管单条消息的花费；整段单聊的总花费不设上限，和 Claude Code、Codex 每个任务默认不限制一致。重启后接着发照常：委派的父是单聊的根时，主机从会话重建根智能体（GRP-19）。套了岗位说明书的外部联系人，说明书经委派的 `instructions` 追加。用户自己发的消息就是同意，不再弹「允许交给它」的卡片；它运行中的提问出现在它的对话页。
  - 打开：档案里「发消息」、Group 首页只 @ 它们，都打开它们的单聊。还没有消息时是单聊首页，输入框是简单的一行（「给 Codex 发消息」，下面写「单聊里它只读、不改文件」）；有了委派之后，单聊直接打开委派的对话页（复用子智能体对话页 `ExternalAgentConversation.vue`），路径写「联系人 / 单聊」，‹ 回到联系人档案。对话页里发消息、停止、回答它的提问都照常。再次打开同一个单聊（页面被保留时也一样）都直接到对话页；查询或发送回来时用户已经离开，就不再把人带回去。输入框里没发出的字跟着各自的单聊；联系人列表读到之前，单聊的输入框写「正在读取联系人…」、不收字。单聊首页不显示常用起手式（它们只填普通输入框）。
  - Core 守卫：`chat.submit` 发到它们的单聊报 `contact_chat_external`；主机在送达和每一步之前也拒绝（群成员会话、后台回合同样不会让本地模型代它们说话）。联系人删除后，它的单聊和委派对话页都只能查看（`contact_deleted`；对话页的输入框也写「这个联系人已删除，这个会话只能查看」）；归档的单聊仍写「联系人 / 单聊」，‹ 回到档案。
  - 发不出去时（GRP-19）：`contact_chat_failed` 带一句单聊自己的中文，说原因和做法（没登录、正在停下上一条、排队太多、上次没正常结束要先「标记为已结束」、太长要分几条……），不出现内部码、执行器的英文或群聊里的「@ 它」；原始错误只写进 core.log。一条消息最多 32 KB，超了发之前就拒绝。同时发出的两条首条消息只开一个委派，单聊跟着最新的、没关闭的那个委派。
  - 档案页写「单聊里它只读、不改文件；要它改代码，在 Build 对话里把任务交给它。」
- 外部联系人（Claude Code、Codex）也可以套一份岗位说明书，例如「Claude Code · 安全审计」：通过两个执行器各自的追加指令入口生效，模型和权限跟随「设置 › 子智能体」。
- 删除（GRP-16）：档案「编辑」旁的「⋯」里是「删除联系人」，内置联系人没有「⋯」。先用确认框说清后果（单聊留着、只能查看；退出所在的群，说过的话留着；历史版本和个人记忆一起删除，不能恢复），确认后 `contacts.delete`，回到 Group 首页并重读联系人和群的列表。Core 删掉联系人后让它退出每个它在的群（`group/member` 的 `removed`，和「移出」一样：成员会话和消息都留着，它主持的群改为没有主持人），每个群发一次 `groups_changed`（`member`）。在这之前删掉的联系人如果还在某个群的成员里，群设置和成员栏把它显示成「已删除的联系人」（`missing`），可以移出。

## 群聊

### 群设置与成员工作区

| 设置                 | 默认 | 说明                                                               |
| -------------------- | ---- | ------------------------------------------------------------------ |
| 群公告               | 空   | 每位成员发言前都会读到：目标、约束                                 |
| 每轮结束时群聊出结论 | 开   | 本轮使用内置协调且已有成员发言时，由群聊生成结论；结论用浅金底显示 |
| 防打转               | 开   | 见下文「停下来」；内置协调可介入换人或收尾                         |
| 安静模式             | 关   | 只回应 @：没人被 @ 就没人说话                                      |

全部群统一采用**自主协作**：没人被 @ 时，和职责有关的成员举手；成员之间可以直接点名、直接交办。Core 为新群自动补入且只保留一位固定可见成员 `ct-emperor`，旧群迁移时补齐；它不能被移出，12 人上限包含它。内置协调的安排、简短状态、提问和收尾都以 Emperor 的普通消息呈现，不形成第二套自主声音，也不是可由用户切换的审核模式。历史日志里的 `moderated` 只作兼容输入，重放后仍归一为自主；历史主持人消息和旧事件保留，但不能恢复成员间发言先审核的旧流程。用户自己的 @ 和交办不需要审核；改代码仍按原有权限与确认规则执行。

每个群有 Core 管理的独立工作区，不要求用户选择项目或配置 Git：

```text
<stateRoot>/groups/<groupId>/
  members/<contactId>/       # 该成员日常工作区
  shared/artifacts/<artifactId>/<filename>  # 宿主发布的公开成果
```

成员只能读写自己的目录、读取共享区；其他成员目录在只读、工作区可写和完全访问模式下都属于拒绝范围，Shell 的完全访问守卫也同样拒绝写 shared。需要公开的文件或图片由 Core 宿主从本人目录复制到共享区，按 SHA-256 生成不可变 `artifactId` / `artifactRef`，并记录作者、来源 taskId、MIME、大小和内容摘要；`artifactId` 就是提交与检查使用的 revision。同一文件重复发布保持同一 ref，同名不同内容生成新版本，同一内容的不同文件名不会互相覆盖投影。公开事件不记录成员私有源路径，群消息只携带 ref，不内嵌大文件。群会话和该群成员会话可经现有 `references.resolve`、文本/图片预览和 Finder 定位权限读取公开成果，其他会话即使拿到 ref 也不能解析；共享文件不会自动执行。成员退出后旧目录和成果保留，但不能再写或发布。成员目录不是 Git worktree，共享区也不是代码集成入口。外部适配器没有宿主强制路径能力时不得宣称已隔离，当前外部成员统一只读串行，文本报告由宿主发布。只读本地成员复用同一宿主中介路径，最终正文先保存到本人目录再发布，不能因此放宽其他成员私有目录。

### 五种发法

每条群消息都带「受众」。受众决定谁的上下文里有这条消息，点名决定谁要回答。**用户能看到全部消息，包括成员之间的私信**；没有用户看不到的 agent 间通信。

| 发法     | 怎么发                            | 谁能看到                       | 谁要回答                                                     | 界面上                                                 |
| -------- | --------------------------------- | ------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------ |
| 广播     | 不 @ 人，或 @所有人               | 全体成员                       | 有关的人举手；无人认领时由内置协调兜底；安静模式下没人回答   | 「→ 所有人」                                           |
| 点名     | @A，或 @A @B                      | 全体成员                       | 只有被 @ 的人；多人按 @ 的顺序接力，后一位能看到前一位的回答 | 「→ @A」，@ 高亮                                       |
| 独立作答 | 广播或点名时选「各自独立回答」    | 全体成员，但作答期间彼此看不到 | 被问到的人同时答（最多 3 位并行），都答完后一起显示          | 揭晓前不占消息行、右侧显示 N/M；揭晓后逐条普通成员消息 |
| 私信     | 用户：发给 → 私信；成员：私信工具 | 只有对方（和发送者）           | 对方                                                         | 紫色左边线和「🔒 私信 · 其他成员看不到，你能看到」     |
| 交办     | 用户：发给 → 交办；成员：交办工具 | 全体成员                       | 被交办的人去做一件有交付物的事                               | 交办、接单和交付均为普通消息；任务状态在右侧           |

成员怎么说话：轮到它时，它在自己的成员会话里正常干活，最后的回答就是一条群消息。正文里写 `@全名` 就是点名下一位；不点名，这条线就说完了。成员读到的群说明列出每位成员的全名和简介，点名时照抄全名。本地成员另有私信、交办和「我没有补充」工具；Claude Code、Codex 只能用正文里的 @。交办链不能绕回：A 交给 B 的任务，B 不能再交回 A 或链上的任何人。旧日志中的成员主持人专用 `group_next` / `group_close` 只为回放兼容保留，新群和内置协调群不向成员提供这些工具。

成员发言里的 @ 怎么认（GRP-15）：先按全名认，长的名字优先（`@Claude Code` 不会认成 `@Claude`，「@反方（红队）」连括号一起认）；全名对不上时，@ 后面这个词去掉结尾的标点、反引号和引号（「`@反方`」里的「反方」），只要是**恰好一位**成员名字的开头（至少 2 个字）就算点了这位：「@反方」就是「反方（红队）」。几位成员的名字都这样开头时不猜，说话的成员收到一条只有它和用户看得到的提示：「「反方」能对上好几位成员：反方（红队）、反方（蓝队），请写全名；这次点名没有送达。」谁都对不上时提示「「X」不在这个群里，这次点名没有送达。群里的成员：…。」同一个名字在一条发言里只提示一次；邮箱地址和带 `/` 的路径不算 @。成员用私信、交办工具指定对象时也按这个规则认名字。

成员读到的交办是整件任务（GRP-17）：投递给成员的群消息里，一项交办写成「[10:42] 审稿人 → 所有人（交办给 架构师）：查溢出」，下面跟着交付物、依据和权限，不只是标题。一位成员被点名发言时，如果还有交给它的任务排在后面，它的提示里多一句「交给你的任务「查溢出」稍后单独交给你，到时再做；这次只回应上面的消息。」这是 GRP-10 正反方验收里看到的：成员先被点名，从标题猜着把任务做了，真正的任务到了反而当成旧内容重放。

### 停下来

群聊**不设本轮额度**：不限发言次数、轮数和费用，也没有花费提醒，标题栏只实时显示「本轮 ¥… · 不设上限」。防打转里唯一的次数是交办接力的 3 次，它只让这一轮停下来等用户，不是额度。一轮会在这些时候停：

| 情况                             | 结果                                                                                                                                                                         |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 没人被点名，排队也空了           | 本轮自然结束；本轮用过内置协调且开启总结时，由群聊生成结论                                                                                                                   |
| 内置协调认为问题答完了           | 群聊生成系统结论并结束本轮；不伪造成某位成员发言                                                                                                                             |
| 两位成员来回没有新内容（防打转） | 按「有没有新内容」判断，不按次数：同一对成员连续来回 4 次以上且最近两次几乎没有新内容时，内置协调介入换人或收尾；无法协调时暂停并问用户                                      |
| 交办接力（防打转）               | 同一位成员在一轮里已经有 3 次发言交办了任务（一次发言交出几项只算一次），它下一次交办的任务先不开始，本轮暂停，群里写明原因；用户回复「继续」就接着做，计数随新的一轮重来    |
| 连着「没有补充」（防打转）       | 成员说「没有补充」时，它已经读过之前所有的消息，排队里还在等它回答的点名都撤掉；等被点到的人都说了「没有补充」，排队空了，本轮立刻结束，按「每轮结束时群聊出结论」的设置收尾 |
| 用户发了新消息                   | 正在说的人说完这一段，排队的人按新消息重排                                                                                                                                   |
| 用户点「停止」或按 ⌘.            | 停止发言：正在说的人停下，没发出的发言和旧简单前台交办丢弃；扩展后台任务不受影响                                                                                             |

「设置 › 用量与费用」页（0.3 由原来的「用量」页扩成）里的防失控限制（一次回答最多调用工具 400 步）和费用上限（默认不限制）**按每位成员的每一次发言单独计算**，不累计成整轮的额度：一次发言被截停时，群里写明原因，其他人照常。

### 后台工作队列（CG-03）

扩展 `GroupTask` 与发言共用群日志和任务事实，但由独立后台工作者执行：依赖已验收且版本有效的任务由 Core 原子接单，默认每群最多 2 个、全局最多 4 个；长任务不占发言队列，短发言仍可及时完成，独立作答仍在全部答完后一起揭晓。没有写、停止和结果收集能力的适配器降级为只读串行；它收到写任务时明确失败为 `adapter/readonly`，不冒充隔离或并行。

后台回合结束不等于任务完成。可写本地成员只能在当前活动工作会话里用 `group_task_submit` 把本人工作区文件发布为不可变公开成果，再按精确 attempt/lease 提交；普通回复不能改变这类任务状态。只读本地成员没有提交工具，宿主把它非空的最终正文保存为本人目录中的报告并生成公开成果和通过检查，再完成同一任务；空正文仍是 `missing_submission`。要求真实写文件而成员只有只读能力时在模型执行前失败为 `adapter/readonly`。有效提交要求精确成果 revision、非空且全部通过的检查依据，满足后任务直接自动完成，不再等待用户确认。旧 `submitted` 事件和 `accept` API 只为历史回放兼容保留。移交或新 attempt 会撤销旧执行权，旧 run 的迟到结果不能覆盖新成果；失败保留已经公开的成果，并记录可解释的问题原因。

停止分成两个 Core 命令：`groups.stop` 只停止发言和旧简单前台任务；`groups.stopWork` 请求停止扩展后台任务，并直接取消尚未启动的 queued 任务，避免空位释放后自动补位。运行中的任务要等执行器确认停止后才取消并释放工作者。删除群聊会停止并等待两个队列都收尾。

应用重启时先探测活动 attempt 对应的旧会话或委派记录，不自动重跑旧活动 attempt。无法确定结果的标为 `failed`，同时保存 `problem.kind = 'unknown'` 和重启原因；已确认停止的标为 cancelled。从未启动的 queued 任务可以恢复调度。

### 群聊页

点开一个群（侧栏、Group 首页、搜索、通知）进 `/groups/:groupId`（GRP-08）；群自己的会话从 `/chat/:id` 打开时也转到这里。

- 头部：群名、人数、「自主」标签（安静模式时加「· 安静」），右侧「本轮 $… · 不设上限」、「停止 ⌘.」和群设置。花费用美元，和「设置 › 用量与费用」一致。
- 消息流只保留对话（D54）：用户交办原文、Emperor 的一次性安排 / 失败说明、成员一次接单、最终交付和已揭晓的独立答案都按普通消息显示，不再出现任务卡、独立作答卡、公开成果卡或外部执行结果卡。成员在左、用户在右，32px 头像和 QQ 式紧凑气泡；同一人的连续消息约 5px、不同发言人约 16px。公开正文超过短消息边界时先生成摘要，摘要失败只提示到右侧看完整内容，绝不回退为发布原始长文。未揭晓的独立答案不占消息行，正文不会提前泄露。交付消息中的公开文件和图片作为内联附件，复用文件类型图标、大小、查看 / 获取和共享图片查看器；不把成员私有路径或私信放进 shared。没有“确认验收 / 确认完成”等人工 Agent 操控入口，运行期间也不显示虚构百分比。已删除的联系人显示灰色头像和「已删除的联系人」。
- 成员发言在写入群日志之前按实际开始时间进入统一消息流：头像、名字、「发言中」和光标；工具调用前已经公开的正文保留，后续正文接在同一草稿，写完由群日志里的最终消息接上并去除草稿。各自独立回答在揭晓前不显示草稿；Claude Code、Codex 仍是一次性结果，只显示「发言中 / 执行中」。
- 成员的工具步骤、任务状态和独立作答进度不进主消息流。普通发言和流式草稿不提供「过程 ›」按钮；点击右侧成员只在右侧打开其**本群成员会话**的真实只读工具记录，不跳转联系人档案、私人单聊或其他群。计划审阅和电脑操作授权仍可从对应安全提示进入处理页面。
- 成员发言时要用户回答的问题（`ask_user_question`）和要批准的操作，像群里的一条消息一样出现在那位成员名下（D29）。提问前的公开短文以 `interactionId` 持久化为来源消息，提问卡紧跟这条消息；后续发言和最终回答不会改变锚点。内置协调的 clarify 也走 Emperor 成员会话的真实控制提问链，不能用普通正文冒充提问卡。没有提问前正文时不制造空消息，只有旧日志按时间兼容回退：问题的选项是消息里的快捷回复，只有一个单选问题时点一下就回答；也可以自己写一句；「不回答」取消这个问题。审批写明要做什么，按钮和对话里的一样（拒绝、允许本次……；Claude Code、Codex 第一次用时是不允许 / 本次允许 / 以后都允许）。计划审阅和电脑操作授权写一句「等你处理」，「去处理 ›」打开它的工作过程。回答之后问题离开消息流，群日志里记一条只给你看的系统消息（GRP-12）：「你回答了 架构师 的提问：…」「你批准了 架构师 的请求：…」「你拒绝了 …」「你没有回答 …」（计划审阅是「你批准了 … 的计划」「你对 … 的计划提了意见」），居中小字，回答的是哪个问题悬停可见；重开群页面、重启后都还在。在成员的工作过程里回答的也记。它不是群消息：不投递给任何成员，不进群纪要，不算发言次数（提问的成员从自己的会话里拿到回答）；电脑操作授权不记，停止一轮时取消的提问也不记。旧日志中等待人工确认的任务仍按普通消息回放，不再显示「同意 / 不同意」或验收按钮；安全问题与权限审批仍按上述 D29 规则处理。
- 输入框：「发给 ▾」五种发法：所有人 · 举手（文字里 @ 了成员就按点名发）、所有人 · 各自独立回答（没有 @ 时问除「只在被点名时」发言的成员以外的每一位）、@ 指定成员、私信…（选一位成员）、交办…（选一位成员，填任务、交付、依据和权限：只写群文件 / 只读 / 在隔离副本里改代码；发出后回到「所有人 · 举手」）。@ 补全只列群成员（↑↓ 选择、Enter 或 Tab 确认、Esc 关闭）；选中的名字在输入框里高亮（整名、词首才算，`a@b.com` 和 `@研究员员` 不算），字号、字重和内边距不变，所以光标和换行不漂。Enter 发出，Shift+Enter 换行，⌘/Ctrl+Enter 也可以发；补全列表打开时 Enter 选人，Shift+Enter 改为换行。@ 了不在群里的名字时不发送，下面一行说明原因。
- 输入框上方一行：正在发言、排队（交办的标「（交办）」），右边「本轮 3 分 12 秒 · 7 次发言 · $0.86」。一轮结束后写它怎么结束的（已结束、已停止、已暂停：两位成员来回没有新进展、同一位成员交办的次数多了，回复「继续」接着做、大家都没有补充、应用重启时停下，可以重发）。
- 右侧成员栏：「成员 N」和「+ 邀请」，每人一行显示真实状态。下方只读显示任务进度（负责人、接单、执行检查、公开成果、自动完成）和独立作答的 N/M；未揭晓时只有「答完一起显示」，没有答案文本。点击成员只切换右侧执行详情，详情来自该成员在本群的 session 投影；没有会话时不伪造记录，也不一直停留在加载态。宽度不超过 1080px 时由顶部按钮打开右侧覆盖式抽屉，可用遮罩或 Escape 关闭。
- ⌘. 在有进行中的一轮时停止它（有对话框打开时不响应）。
- 侧栏的群那一行在有人发言时写「架构师 发言中…」「架构师 等 2 人发言中…」，只有人排队时写「排队：研究员」，空闲时照旧「N 人 · 时间」（GRP-13，见 [modes.md](modes.md)）。

#### 群设置

`/groups/:groupId/settings`，标题栏「群设置 / 群名」，「‹」回到群里。依次是：群名（改完离开输入框保存）、群公告（「保存公告」）、「每轮结束时群聊出结论」「防打转」「安静模式」三个开关（改了立即保存）、成员（移出、邀请）、群文件（只列名字），最下面是「删除群聊」（淡红色按钮，GRP-16）。保存失败时提示，并回到原来的值。

#### 删除群聊

「删除群聊」先确认（「群聊和每位成员的工作过程一起移到「设置 › 常规 › 已归档对话 › 最近删除」，30 天内可以恢复，之后自动清除。进行中的一轮会先停下。」），确认后 `groups.delete`，回到 Group 首页。删除和删一个对话一样进最近删除，只是一个群连着几个会话：

- Core 先停止发言和扩展后台工作，没说完的发言丢弃、queued 后台任务取消，并等运行中的执行器确认收尾，再把群自己的会话和每位成员的会话（移出过的成员也算）在同一时刻移进 `sessions/.trash`，发 `groups_changed`（`deleted`）。群从 `groups.list`、侧栏和 Group 首页消失，群文件留在原处。会话索引里只剩这个群的会话时也照样删除（群不会是 Chat 的最后一个对话）。
- 最近删除里一个群只有一行，写「群聊 · 日期 删除」。恢复它，成员会话一起回来，群原样回到列表（`groups_changed` 的 `restored`）；永久删除它或 30 天到期，成员会话、它们的回合快照和委派，以及 `groups/<群 id>/` 下的群文件一起删除。

#### 新建群聊

侧栏的「新建群聊」（Group 下的 ⌘N）、「群聊」标题旁的「+」和 Group 首页的「新建群聊」卡片打开同一个对话框：先选模板——评审（架构师、代码审稿人、测试工程师）、正反方（产品经理、反方（红队））、调研写作（研究员、写作者、编辑）——或空白。成员区先单独显示固定的 Emperor 和「默认内置」，没有复选框；模板只填群名、群公告并勾选从对应岗位模板建的其他联系人，还没有这种联系人时写「还没有：测试工程师」和「去新建联系人」。`picked` 与 `groups.create.members` 只含其他成员，Core 自动补入且去重 Emperor；空白群可以不选其他成员，总人数和 12 人上限始终包含 Emperor。对话框只有「1. 群名称」「2. 成员」「3. 可选群公告」；成员说明告知每人在独立工作区自主执行，需要公开的文件再发布到群共享区。建好后打开新群。

#### 新群的默认设置

「设置 › 群聊」（和「子智能体」在同一组）的「新群的默认设置」只保留防打转（默认开）。所有群都由成员按职责自主协作，没有协作方式选项；新建群采用这个防打转默认值，已有群保留自己的设置。

### 空状态与错误

- 没有群：「把几个联系人拉进一个群，让他们一起讨论；你随时可以插话」+「新建群聊」（模板：评审、正反方、调研写作）。
- 成员的模型不可用：那次发言失败，群里一条系统消息写明原因（「X 这次发言失败：…」），其他人照常。
- 外部成员没登录、版本不兼容：群里一条系统消息，带和「设置 › 子智能体」一致的按钮。
- 应用重启时进行中的一轮标记为已停止，用户可以重发。
